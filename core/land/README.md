# core/land — land 판정 함수 · 실행

sangsoe 가 PR 을 머지하는 유일한 길이다(결정 72·81·85, 부록 `#role-cards`). 사전 확인(`--dry-run`)·실행·거부 문구가 같은 함수 하나이고(R-03), 셸에서는 `sangsoe land`, 에이전트는 MCP tool `land` 로 부른다.

- `land.ts` — `land(input, deps)`. 순서: 입력 → PR 읽기(열림·draft 아님·`--head` 와 같음) → main 동결(그 저장소의 마지막 `main_red`/`main_green`, `--main-fix` 만 통과) → 스택 순서(`stacked_on` 선행이 `pr_merged`) → 죽은 base(기본 브랜치가 아닌 지금 base 를 head 로 쓰는 다른 PR 을 GitHub 에서 읽어, 열려 있으면 `stack_order`, 머지됐으면 `base_merged`, GitHub 의 base 가 기록된 base 와 다르면 `base_unrecorded`, 결정 216) → 리뷰 판정(`review_verdict`, 마지막 `pr_base_changed` 뒤에 기록된 것만 세고 없으면 `rereview_needed`, 다른 head 는 patch-id 가 같을 때만 승계, 결정 215) → 등급의 증거(`core/verify`) → 조건 넷(`core/gh` 의 `readMergeConditions`, 설정에서 참이 아닌 (1)–(3) 은 `ownConditions` 가 스스로 확인해 `source: own` 으로 바꾸고, 머지하는 길은 그 확인이 실패하거나 읽히지 않으면 거부한다. 결정 204. 보호나 rulesets 를 못 읽었으면 (2) 는 compare 가 아니라 GitHub 의 `mergeable_state` 로 보고 `behind` 일 때만 `behind_base` 다, 결정 304) → `gh pr merge --auto` 또는 GitHub 승인 뒤 머지, 아니면 `land_requested{merge_on_approval}`. head 에 승인이 이미 있으면 `merge_on_approval` 이 아니라 막은 것(own 조건 · `not_mergeable` · rollup 의 `checks_*`)으로 거부하고, 승인이 없으면 그 note 가 왜 없는지(다른 head 의 승인 등)를 말한다(결정 304). 설정 `verdict_merge_repos` 에 든 저장소는 자동 예약이 안 되고 head 에 GitHub 승인도 없을 때 `merge_on_approval` 대신 정확한 head 의 기록된 판정·초록 검사·풀린 스레드를 읽고 바로 머지한다(`--match-head-commit`, `land_requested{verdict_approved}`, 결정 158). 거기서 V3·보호 경로는 오너가 오케스트레이터 대화에 친 그 PR·정확한 head 의 `owner_approval` 이 있을 때만 같은 길로 머지하고(`merge_owner_approved`, `land_requested{owner_approved}`), 없으면 note 에 그 줄 `승인 <owner/repo>#<N> <head>` 를 적고 기다린다(결정 311). PR 을 읽은 뒤의 거부는 모두 `land_failed{reason}` 한 줄이다(dry run 은 쓰지 않는다).
- `github.ts` — land 와 verify-tier 가 쓰는 GitHub 읽기(`core/gh` 클라이언트로, 결정 158 의 head·스레드·필수 검사 GraphQL 한 번만 `gh api graphql`), patch-id, `approvalAtHead`(그 head 의 믿는 승인, 없으면 왜 없는지)·`approvedAndGreen`(pr-monitor 의 승인 깨움), `containsBase`(compare `base...head` 가 `ahead`·`identical` 인가, 결정 204), `mergeConfirm`(GitHub 의 머지 표시 + 머지 커밋이 기본 브랜치에 포함, 둘 다 참일 때만 참; 부르는 쪽은 pr-monitor).
- `ports.ts` — 실제 의존: store, gh 클라이언트, 설정(`~/.config/sangsoe/config.json`), 그리고 GitHub 에 쓰는 두 호출: 머지 예약 `ghMerge`(결정 0124)와 바로 머지 `ghMergeNow`(결정 158).
- `rereview.ts` — base 변경 뒤의 재리뷰 판정(결정 215): land·pr-monitor 의 머지 가능·GRAPH 의 재리뷰 항목과 why 행이 같은 함수로 본다.
- `tier.ts` — `sangsoe verify-tier` 의 읽기 전용 함수. `tier_source` 는 `config` 이거나 `none (fail-closed V3)` 과 빠진 목록이다(결정 172).
- `record.ts` — land 와 GRAPH 가 읽는 두 줄의 기록 함수: `recordEvidence`(PR 의 현재 head 에 `evidence`)와 `recordStage`(머지된 PR 에 `stage_recorded`). 작성자와 head 는 GitHub 에서 읽고 기록자가 작성자이면 거부한다. 입구는 MCP `evidence_record`·`stage_record` 와 CLI `sangsoe evidence record`·`sangsoe stage record` 다(결정 171).

거부 사유와 설정 키는 `docs/decisions.md` 결정 124, 등급과 증거는 결정 125, 계정 하나인 저장소의 바로 머지는 결정 158, 보호를 못 읽을 때의 자체 확인은 결정 204.
