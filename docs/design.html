sangsoe 설계안

상쇠(sangsoe, [sang-soe])는 풍물패 앞에서 꽹과리 신호로 패를 이끄는 사람이다. 이 한 장이 통합 설계안이고 처음부터 읽으면 된다: 무엇을 만드는가 → 네 칸 배치 → 컴포넌트 → 데이터 → 흐름 → 구현 순서와 전환. 각 절은 결론과 이유를 본문에 쓰고, 상세는 부록에 링크한다. 부록: design-appendix.html(스키마·역할 카드·전달 규칙·기존 설계 조사) · decisions.md(결정 전체) · glossary.md(용어집, 용어의 정본) · port-plan.md(agent-skills 에서 무엇을 참조하나) · dashboard/hallmark-final/(패널 시안).

1. 무엇을 만드는가

sangsoe 는 여러 Claude Code·Orca 세션에 나눠 맡긴 일을 Orca 위에 기록하고, 막히면 필요한 쪽을 깨우고, 끝난 일에 증거가 없으면 표시하는 하네스다. 항목·의존·게이트·메시지는 Orca 가 원본이고, sangsoe 는 Orca 에 없는 것(오너의 말, 결정 키, 부가 간선, PR 사실, 자원·신호 기록)을 sqlite 에 쌓는다. 모델 바깥의 환경(hook · 게이트 · sqlite event · Orca 메시지 · 감지기)이 일의 기록과 깨움을 맡고, 모델이 혼자 못 지키는 것(기록 · 같은 질문 막기 · 머지 순서 · 정리)을 코드가 지킨다. 원칙은 하나다: Orca 가 기능을 제공하면 그것을 쓴다.

이다
  • 원본은 기능이 있는 쪽: 항목(Orca Task)·만들 때의 의존·게이트·메시지·Dispatch·Run 은 Orca 가, 오너의 말·결정 키·Orca 에 없는 간선·부가 정보는 sangsoe sqlite 가 쥔다. sangsoe 는 Orca id 만 들고 사본을 두지 않는다. Orca 를 못 읽으면 그 값은 "모름"이다.
  • sangsoe 의 기록은 하나: sqlite 의 event 표. 줄만 더하고(append-only) 고치거나 지우지 않는다. 항목의 현재 상태는 뷰가 Orca 읽기와 event 를 합쳐 만들고 합친 결과를 저장하지 않는다.
  • 깨움은 따로: event 는 기록이고 깨우지 않는다. 사람이 아닌 쪽을 깨우는 것은 Orca 메시지 하나뿐이다.
  • 기다리는 일은 한 곳: 지금 돌고 있지 않은 일은 Orca Task(pending·ready·blocked)와 열린 Orca 게이트로만 기다린다. 파일 큐도 채팅 속 약속도 없다.
  • 판단만 토큰을 쓴다: 감지·실행은 hook 과 스크립트라 토큰이 들지 않는다. 오케스트레이터·리드·워커만 LLM 이고 Orca 메시지로 깨어났을 때만 쓴다.
  • 일의 순서(의존 간선 · 흐름 틀 · 크리티컬 패스)에만 그래프를 쓴다.
아니다
  • 에이전트 모델도 실행 환경도 아니다. 세션은 Claude Code 가, 터미널·워커·메시지·Task·게이트는 Orca 가 맡고 sangsoe 는 그 위의 기록과 신호만 둔다.
  • LangGraph 같은 고정 그래프가 아니다. 오너 지시와 에이전트 대화는 그래프로 묶지 않고 event 기반 상태 기계로 돈다.
  • MCP 는 저장소가 아니다. MCP 서버를 에이전트의 입구로 내지만 MCP 는 인터페이스일 뿐이고 상태는 Orca 와 sqlite 에 있다.
  • 정기적으로 훑는 LLM 작업은 없다. 정기 감지는 모델 없이 도는 monitor 이고 Orca plugin worker 안에서 돈다. 자체 상주 프로세스·포트·웹 서버는 없다.
  • 일반 스킬·오너 개인 도구는 본체가 아니다. 일반 작업 스킬은 sangsoe 의 역할·상태에 기대지 않고, ③ Claude Code plugin 안 claude-plugin/skills/general/ 에 따로 둔다(결정 95).

설계 관점

sangsoe 를 세 관점으로 읽는다. 업계에 합의된 정의가 없어 이 문서가 쓰는 뜻은 용어집에 적었다. 결론: harness 가 중심이고, loop 는 역할마다 다르며, graph 는 일의 순서에만 쓴다.

  • harness engineering: 중심이다. 모델 바깥의 환경을 만든다: hook · 게이트 · 거부 규칙 · sqlite event · Orca 메시지 · 감지기 · REAPER. 모델이 혼자 못 지키는 것은 규칙으로 두는 것보다 코드가 지키게 해야 어긋나지 않는다.
  • loop engineering: 역할마다 다르다. 워커는 브리프의 끝나는 조건으로 돌다 증거를 담은 worker_done 한 번으로 멈춘다. 리드는 Orca 메시지를 기다리고(check --wait) → 처리하고 → 다시 기다리며, 프로그램의 완료 조건을 채운 증거가 event 에 있으면 worker_done 으로 멈춘다(결정 121: 끝은 /goal 이 아니라 Dispatch 와 worker_done). 오케스트레이터는 Orca 메시지로만 깨어나고 처리한 뒤 다시 잠든다. 정기적으로 훑는 LLM 루프는 없고, 루프마다 멈추는 조건이 하나씩 있다.
  • graph engineering: 일의 순서에만 쓴다. 의존 간선·흐름 틀·크리티컬 패스에 한해 그래프를 쓴다. 오너 지시 흐름과 에이전트 대화 경로는 매번 오너의 말과 Orca 메시지가 정하므로 그래프로 고정하지 않는다.

2. 네 칸 배치

결론: 모든 기능과 컴포넌트는 아래 네 칸 중 정확히 하나에 놓는다. 판정은 위에서 아래로 하고, 앞 칸이 할 수 있으면 뒤 칸에 만들지 않는다. ① Orca CLI 내장 기능은 만들지 않고 그대로 부른다. ② Orca plugin 은 Orca plugin 이 할 수 있는 것을 전부 싣는다. ③ Claude Code plugin 은 Orca plugin 이 못 담는 것(hook · skill · MCP 서버 · agent 정의)만 싣는다. ④ 공유 코어는 두 plugin 이 같이 쓰는 TS/Node 코드와 sqlite 와 CLI 다. 두 plugin 은 한 저장소의 매니페스트 둘이고, 서로 직접 통신하는 공식 경로가 없어 연결점은 공유 코어(sqlite)와 Orca CLI 둘뿐이다. 같은 일을 하는 입구가 칸마다 달라지면 시험과 권한이 입구 수만큼 늘어나서 이렇게 둔다.

결론: 오너는 Orca 메시지를 직접 받지 않고 현황 세 단계로 본다. 현황(1단계)은 표 네 절(결정 필요 · 지금 오너가 할 일 · 열린 항목 · 보류)이고 리드·카드·PR·워커가 한 행씩이다 → 묶음 상세 → 항목 상세. 같은 모델을 sangsoe brief 와 Orca plugin 패널이 쓴다. 화면은 읽기 도구이고 버튼은 패널 → plugin worker → 코어의 같은 함수를 불러 owner_action 으로 기록된다. 127.0.0.1 웹 대시보드는 없고 별도 서버도 포트도 수집기도 없다. 이유: 화면이 스스로 만들면 원본이 둘이 된다. 패널은 오른쪽 사이드바에 그려지므로 같은 열을 행마다 한 블록으로 접는다(열을 빼지 않는다).

상태🔄진행 중살아 있는 워커나 리드가 쥐고 있다. 결정이 풀려 Orca 상태가 ready 가 됐어도 워커가 아직 쥐고 있으면(활성 Dispatch) 🟢 가 아니라 🔄 다.
상태🚧막힘시작했으나 누군가 없이는 못 간다. 기다리는 쪽을 괄호에 적는다(오너·리뷰어·인프라·리드·워커). 리뷰 대기도 막힘(리뷰어)이고, land 요청 뒤 머지를 기다리는 PR 항목도 같다.
상태⏸️보류일부러 지금 안 한다. 다시 볼 trigger 가 있다. 시작 조건이 글뿐인 항목도 여기다.
상태✅완료Orca Task 가 completed 이고 그 Task 의 PR 이 있으면 머지됐다. 머지 없이 닫힌 PR 의 항목은 ✅ 가 아니라 🚧 막힘(리드, 읽기 pr_closed)이고, PR 상태를 아직 못 읽은 항목은 ❔ 모름(unknown)이다(결정 178, 보기 전용이라 Orca 상태는 그대로다). 그 PR 이 다시 열리면(pr_reopened) 열린 PR 의 항목으로 읽히고(결정 216), 다시 열지 않을 항목은 오너나 리드가 item_retire 로 거둬 🗑️ 취소로 읽힌다(결정 223). verify 가 있는 오너 항목은 누가 Task 를 닫았든 probe 가 통과할 때까지 ⏳ 검증 대기(pending_verify)로 읽히고, 후속도 그때까지 기다린다(결정 181). Task 는 받아들여진 worker_done(PR 작성자도 같다)이나 리드·오케스트레이터의 닫기로 completed 가 되고, PR 이 걸린 항목은 pr-monitor 의 머지 확인(pr_merged) 전까지 🚧 막힘(리뷰어)으로 읽힌다(결정 175). 머지 확인 말고는 sangsoe 의 감지기·스크립트·hook 이 항목을 닫지 않는다. 증거 없이 닫힌 항목은 🔍 로 표시되어 리드가 확인한다.
상태⏳검증 대기오너가 완료라고 한 오너 할 일인데 그 verify probe 가 아직 참을 보지 못했다(결정 181). 닫힌 것이 아니라 진행 중에 세고, 후속은 기다리며, probe 가 통과하면 ✅ 가 된다.
상태🗑️취소하지 않기로 했다. 이유가 필수다. 열린 Task 는 Orca 에서 취소하고(failed+cancelled), PR 이 머지 없이 닫힌 완료 Task 는 Orca 가 되돌리지 않으므로 item_retire 가 sqlite 에 item_retired 한 줄만 써서 거둔다. 거둔 항목은 🚧 수·묶음의 열린 수·크리티컬 패스에서 빠진다(결정 223).
플래그🙋결정 필요오너를 기다리는 열린 결정이 이 항목에 있다.
플래그🚨오류·멈춤오류가 났거나 워커·리드가 멈췄다. sangsoe 를 거치지 않고 만들어진 게이트가 막고 있거나, 부가 정보가 Orca 에 없는 Task id 를 가리키는 경우도 여기 보인다.
플래그⚠️확인 필요trigger_unclear 하나만 뜻한다. 스크립트가 판정 못 하는 trigger 다.
플래그🔍근거 부족일한 세션이 스스로 완료를 판정한 경우. 완료로 닫혔는데 증거 event 가 없거나 모자란 항목에 오른다.

MCP 인터페이스

결론: 인터페이스는 입구 셋이고 저장은 Orca 와 sqlite 다. 코어는 라이브러리 하나이고 그 위에 어댑터가 셋이다: MCP 서버(에이전트가 쓰는 유일한 길, tools 는 행동 9개(item_create · edge_add · edge_remove · flow_expand · flow_step_skip · decision_open · decision_answer · start_unit · item_retire) + land 요청 1개 + 기록 6개(handoff_save · review_ask_record · resource_record · review_record · evidence_record · stage_record) = 16개(결정 160·162·171·195·223. item_retire 는 머지 없이 닫힌 PR 의 완료 항목을 거둔다), 읽기 전용 resources: 현황 표 글 brief(결정 89), 시작할 항목 ready, 모델 선택 표 models(결정 164), 항목 이력 template item_timeline(결정 162)), sangsoe CLI(MCP 를 쓸 수 없는 셸 호출자 여섯 행용, 위 호출 경로 규칙), plugin worker(자기 폴더 밖을 import 하지 않고 orca-plugin/core-link.ts 한 곳으로 코어에 닿는다). MCP 는 인터페이스일 뿐이고 상태는 Orca 와 sqlite 에 있다. stdio 서버는 세션이 끝나면 함께 끝나고 세션마다 서버가 뜨므로 쓰는 프로세스가 여럿이어도 sqlite 파일이 쓰기를 직렬화한다. 깨움은 MCP 로 하지 않고 Orca 메시지가 맡는다. prompts·MCP tasks·skills over MCP·상주 HTTP 서버는 쓰지 않는다. Claude Code plugin 이 MCP 서버를 함께 싣고 입력 스키마와 거부 오류의 모양은 tool 정의가 말해 skill 글에는 판단만 남는다.

4. 데이터

결론: 원본은 기능이 있는 쪽이다. 항목·만들 때의 의존·게이트·메시지·Dispatch·Run 은 Orca 가, 오너의 말·결정 키·Orca 에 없는 간선·부가 정보는 sangsoe sqlite 가, PR·대화 기록·티켓은 각 외부가 쥔다. sangsoe 는 Orca 와 외부 값을 복사하지 않고 id·참조와 sangsoe 만 아는 판단·외부 사실의 변화 사건 한 줄만 저장한다. 같은 사실을 두 곳에서 다른 값으로 보이게 하지 않으려는 것이다. 의존 관리

결론: 일이 서로를 기다리는 관계(스택 PR 의 머지 순서, 머지 → dev 배포 → 확인 → prod, 티켓과 PR, 리드 사이)를 기억이 아니라 데이터로 둔다. 기반은 Orca Task 의 의존이고, sangsoe 는 Task id 를 키로 간선 종류·순환 거부·ready·크리티컬 패스·흐름 틀·감지기 사실과의 동기화만 맡는다. 별도 실행 엔진은 없다. 만들 때 알려진 blocks 는 Orca Task 의 --deps 에, 그 밖의 간선은 sangsoe 의 부가 간선에 두며 한 간선은 한 곳에만 산다. 의존이 기억에만 있으면 순서가 어긋나서 부록에 회귀 시나리오 12개를 두었다.

blocks선행이 끝나야 시작할 수 있다만들 때 알려진 것은 Orca --deps, 만든 뒤에 더한 것은 부가 간선선행이 ✅ 완료(선행이 결정이면 닫힘)

  • GRAPH: 간선을 더하고 빼는 길은 sangsoe graph 하나뿐이다. Orca --deps 에 쓰는 것(만들 때 한정)도 부가 간선에 쓰는 것도 이 모듈을 지난다(순환·없는 항목 거부, 같은 간선은 합침). 같은 모듈이 ready 계산·틀 펼치기·크리티컬 패스·영향 범위를 맡고, 감지기가 알린 외부 사실을 간선에 맞춘다. 결정적 코드라 토큰이 들지 않는다.
  • 준비됨과 시작: Orca 상태가 pending·ready 이고 Orca deps 의 선행이 모두 completed 이며 그 선행에 pr-monitor 가 묶은 PR 이 있으면 머지됐고(결정 178. 흐름 단계인 선행은 예외), 부가 간선·trigger 가 모두 차고 hold 가 아닌 항목을 ready 뷰가 가리킨다(계산하고 저장하지 않는다). Run 을 쥔 리드·오케스트레이터가 이 뷰에서 골라 capacity 를 확인한 뒤 worker-start --task 로 직접 시작한다. 아무도 대신 배정하지 않는다. worker-start 는 ready 인 Task 만 받고 선행이 안 끝난 Task 는 task_not_startable 로 거부한다(확인). 이미 Dispatch 된 Task 의 재시작 거부와 3회 실패 컷오프는 시작 함수가 한다(결정 114): worker-start 전에 Task 상태를 읽어 이미 dispatched 이면 waiting already_dispatched 로 돌려주고, 그 Task 의 세는 실패(worktree 만들기·worker-start 실패, Dispatch 없음)를 event 로 세어 세 번째에 loop_detected 를 쓰고 그 뒤로는 stopped 다. 첫 빌드 시험 T5 가 리드 세션에서 둘 다 확인했다. 선행이 completed 이면 후속이 pending 에서 ready 로 바뀌지만, 선행이 🗑️ 취소(failed)이면 후속은 pending 에 남고 "끊긴 선행"으로 보이며 자동으로 풀리지 않는다(확인). 그래서 취소와 무관하게 순서만 정하는 after 는 부가 간선이다. 다른 Run 의 Task 나 모르는 id 는 의존으로 거부되고, 의존은 만들 때만 걸 수 있어 순환이 생기지 않는다(확인, P1).
  • 순환은 더할 때 거부, 흐름 틀(구현 → 리뷰 → 머지 → dev 배포 → 확인 → prod)은 선언형 틀로 Orca Task 를 위상 순서로 만들어 펼친다(요청 id 를 달아 끊기면 이어서 만든다). prod 단계는 오너만 하는 게이트라 준비됨이 되면 시작하는 쪽이 오너인 🟢 준비됨으로 owner_todo 에 오른다. 크리티컬 패스는 묶음에서 아직 끝나지 않은 항목을 잇는 가장 긴 선행 사슬이다. 자기 PR 이 아직 머지되지 않은 완료 Task 도 끝나지 않은 항목이고, PR 마디에서 나온 간선은 그 PR 이 묶인 항목에서 나온 것으로 잇는다(결정 218). 거둔 항목(item_retire)은 빠진다(결정 223).
  • 일부러 그래프로 만들지 않는 것: 오너의 지시가 흐르는 길과 에이전트 사이의 대화 경로.

5. 흐름

결론: 네 칸은 따로 도는 것이 아니라 흐름으로 이어진다. 두 plugin 은 서로 직접 통신하는 공식 경로가 없으므로 이어 주는 것은 공유 코어(sqlite)와 Orca CLI 둘뿐이다. Claude Code 쪽(hook · MCP 서버)은 코어를 부르고, Orca 쪽(plugin worker · 패널)도 코어를 부르고, 코어가 Orca CLI 로 Orca 에 쓰고 읽는다. 아래 그림은 흐름마다 "누가 → 무엇으로 → 누구에게"를 단계별로 그렸고, 오른쪽 열은 그 단계에서 오가는 것과 원본이 어느 쪽인지를 적었다. 흐름 넷은 유닛 시작 · 결정 · 머지 · 모니터에서 깨움까지이고, 그 앞에 오너 지시 하나가 분류되는 순서가 있다.

오너 지시 하나

흐름 1. 유닛 시작

리드 세션이 MCP tool 로 항목을 만들고 시작을 요청하면, 코어가 Orca Task 를 만들고(task-create --deps) 두 단계로 워커를 시작한다(결정 202). 먼저 agent 없이 worktree 를 만들고(worktree create, 요청자 worktree 가 부모. 오케스트레이터는 worktreeId 를 비워도 되고, 그때 start_unit 이 작업 폴더가 든 가장 안쪽 worktree 를 읽어 밝힌 것과 같은 Dispatch 점검을 한다. 리드·워커는 비우면 거부된다, 결정 217 ②), 그 worktree 의 .claude/settings.local.json 에 행의 advisor 를 쓴 뒤(advisor 가 없는 행이나 예산을 다 쓴 Task 는 advisor 를 끄는 값), 그 worktree 에서 워커를 연다(worker-start --task --worktree id:<그것> --keep-open). create 가 연 셸은 handle 과 setup 유무(none·script·unknown)를 unit_started 에 남기고, 워커가 풀린 뒤 setup: none 일 때만 REAPER 가 닫는다. 새 워커 세션이 뜨면 SessionStart hook 이 CLI 로 코어를 불러 역할 줄과 브리프 경로를 받아 세션에 주입한다. 시작은 항상 코어의 시작 절차 하나를 지나서 ready 뷰·capacity 를 먼저 읽는다.

시작 절차는 lineage 를 지킨다: 오케스트레이터 > 리드 > 워커이고, 워커는 세션을 시작하지 않으며 리드는 리드를 시작하지 않는다. 대체 시작은 없다(결정 94). 필요한 Orca 기능이 없거나(capability_missing) lineage 를 읽지 못하거나 어기거나(lineage_invalid) 중첩 워커 깊이 설정이 막거나(depth_exceeded) worker-start 가 오류로 끝나거나(orca_error) 영수증에 Dispatch 가 없으면(no_dispatch) 시작 함수가 거부하고 signal{kind start_refused, reason} 한 줄을 남긴다. 시작을 요청한 세션은 그 일을 맡긴 쪽에 escalation 으로 올리고(리드는 오케스트레이터에게, 오케스트레이터는 owner_todo 로), 부모는 같은 일을 자기 Run 에서 다시 시작하지 않는다: Task 는 Run 을 넘지 못한다. 깊이가 모자라는 Orca 에서는 오케스트레이터가 리드를 시작하기 전에 그것을 읽고 리드 없이 자기 Run 에서 프로그램을 돌린다. 코어를 거치지 않는 시작(orca agent launch, 프롬프트나 --agent 를 붙인 worktree create, 백그라운드 claude, 직접 부른 worker-start·dispatch)은 막는 hook 이 거부한다.

흐름 2. 결정

결론: 오너가 한 번 답한 결정은 닫히고, 기다리던 쪽에 답이 가고, 같은 질문은 다시 만들어지지 않는다. 막기와 풀기는 Orca 게이트가 하고, 이 일을 기억하는 에이전트는 없다. 판단이 필요한 한 군데(잇기)만 LLM 이고 나머지는 함수라 어긋나지 않는다. 결정 하나에 대기자가 여럿이면 게이트도 여럿이고 질문 문구는 각 게이트가 갖는다(Orca 가 원본). sangsoe 는 decision_key → dNNN → 게이트 id 목록만 갖는다. 게이트를 만들고 푸는 명령에는 Run 을 고르는 인자가 없어 묶인 Run 밖에서는 "Gate not found" 로 실패한다(확인, 읽기는 된다). 그래서 다른 Run 의 결정은 그 Run 을 쥔 세션에 Orca 메시지로 보내 그 세션이 푼다. 게이트가 풀리면 Task 는 blocked 에서 ready 로 전환된다(확인). 워커가 아직 그 Task 를 쥐고 있으므로 이 상태는 🟢 가 아니라 🔄 로 보인다. 게이트를 푸는 쪽은 gate-resolve 마다 뒤이어 막혀 있던 워커에게 notify 로 Orca 메시지를 정확히 한 번 보낸다(답 원문과 dNNN 을 싣는다). resolve 만으로 깨운다고 기대하지 않는다.

흐름 3. 머지와 정리

PR 을 만든 당사자(워커 또는 리드)가 독립 리뷰에서 더 고칠 것이 없을 때 MCP tool 로 land 판정 함수를 부른다. 함수는 먼저 PR 의 검증 등급(V0~V3, 라벨 verify-tier:N 으로 조정하며 내리기는 설정 owners 만 유효하다)이 요구하는 증거가 그 head 에 있는지 읽고, 없으면 land_failed(사유 evidence_missing)로 끝낸다. 증거는 PR 을 쓴 세션이 아닌 리드가 evidence_record 로 기록하고, 그 세션은 실행 출력과 확인하지 못한 것을 리드에게 보낸다(결정 171). 그 세션은 어느 입구로도 기록하지 못한다: 기록 tool 과 기록 CLI(sangsoe evidence record·review record·stage record)가 같은 코어 검사를 지나, 부른 세션의 checkout 이 PR 의 브랜치나 head 를 쥐었으면 recorder_is_author 로 거부한다. CLI 는 Claude Code 가 세션 프로세스에 넣는 CLAUDECODE 가 있을 때 에이전트 세션으로 보고, 없으면 오너의 터미널이라 검사하지 않는다(결정 227, v0.1.5). 통과하면 저장소 설정을 읽고 자동 머지 조건 넷이 모두 참일 때만 gh pr merge --auto 로 머지를 예약한다: ① 필수 리뷰와 필수 CI 가 강제된다 ② 최신 main 이 필수이거나 병합 대기열을 쓴다 ③ 새 push 에 승인이 무효가 된다 ④ PR 이 prod·인프라·보안 경로(경로 목록은 설정 protected_paths)를 건드리지 않는다. 설정을 읽지 못하거나 하나라도 거짓이면 예약하지 않고 land_requested 에 사유 merge_on_approval 을 쓰며, 보고에 "승인되면 머지" 를 적어 Orca Task 에 남긴다. 예외 하나: 설정 verdict_merge_repos 에 든 저장소(작성자 말고는 승인할 계정이 없는 저장소)에서는 그 head 에 기록된 독립 리뷰 판정(Act-on 0, 리뷰어 ≠ 작성자)과 증거·검사·스레드·머지 가능 상태가 모두 차면 GitHub 승인 대신 그 판정을 세어 --match-head-commit 으로 바로 머지하고 사유 verdict_approved 를 쓴다. V3 와 보호 경로는 이때도 merge_on_approval 이다(결정 158). 머지하는 길의 검사 조건은 엄격한 채로 둔다: CI 가 없는 저장소에서 land 가 checks_missing 으로 거부하면 오케스트레이터가 diff 와 head sha 를 확인하고 그 head 에 맞춘 일반 머지를 한다. 이것이 land 밖의 유일한 머지이고, 리뷰와 근거만으로 land 를 통과시키는 길은 v0.1.5 에서 다시 보는 LATER 다(결정 226). 스택 PR 은 base 가 바뀐 뒤에 기록된 리뷰만 세어 그 전에는 rereview_needed 로 거부하고(결정 215), 지금 base 가 이미 머지된 아래 PR 의 head 브랜치이면 그 브랜치에 머지하지 않고 base_merged 로 거부하며 base 를 옮기는 gh pr edit 줄을 fix 로 적는다(결정 216 ②). 만든 당사자는 어느 쪽이든 머지 대기 보고(merge_ready)를 본문에 담은 worker_done 한 번으로 스스로 끝난다(결정 175). 상주하는 머지 실행자는 없다. Orca 는 그 worker_done 으로 Task 를 completed 로 닫지만(새 worktree 에서 연 세션은 Orca 가 열어 두므로 시작한 쪽이 worker-release 로 푼다, 결정 197), 브리프는 PR 이 머지되지 않은 동안 그 항목을 🚧 막힘(리뷰어)으로 읽는다. 예약했으면 사람 승인과 CI 가 찰 때 GitHub 이 머지한다. "승인되면 머지"이면 승인과 필수 검사가 찰 때 pr-monitor 가 pr_ready_to_merge 를 쓰고 소유 리드(없으면 오케스트레이터)를 깨우며, 리드가 같은 land 요청을 다시 불러 판정 함수가 조건을 다시 읽은 뒤 예약 없이 바로 머지한다. 머지하는 길은 land 하나이고(예외는 위 결정 226 의 CI 없는 저장소) prod·인프라·보안 경로 PR 도 승인되면 이 길로 리드가 머지한다. 머지 뒤에는 어느 쪽이든 pr-monitor 가 GitHub 이 머지로 표시했는지와 그 머지 커밋이 main 에 들어 있는지를 읽고(머지 확인), 둘 다 참일 때만 pr_merged 를 기록한 뒤 같은 라운드에서 그 항목의 Task 가 아직 열려 있으면 completed 로 닫는다. 패널의 ✅ 는 이때 처음 뜬다. 검증 등급은 release·deploy 의 dev 확인을 덜어 주지 않는다: 머지가 release·deploy 를 일으키는 항목(deploys_after 간선이 있다)은 V0 PR 이라도 dev 칸 증거가 없으면 ✅ 가 되지 못하고 🔍 로 남고, prod 칸은 사람 승인과 prod 증거를 따로 요구한다. pr_merged 는 deploys_after 후속을 준비됨이 되게 하고, pr-monitor 는 그 sha 의 main CI 를 읽는다(위 "머지 뒤 main 감시와 동결"). 빨강이면 🚨 와 동결이다. 그 뒤의 정리는 REAPER 의 타이머 라운드가 표시 → 정리 두 단계로 한다. 기록 없는 기존 카드는 먼저 편입하고, 루트에 닿지 않는 후보 가운데 끝남 판정이 긍정(gh 로 PR 이 머지되었거나 닫히고 HEAD 가 그 PR 에 실림 · 항목 완료·취소·대체 · worker_done 이나 머지 대기 보고)이고 서로 다른 두 라운드에서 연속 후보였으며 유예가 지난 카드만 대상이 된다. 잠잠한 카드라는 이유로는 치우지 않는다. 대상은 삭제 전에 커밋 안 된 변경(추적 안 된 파일 포함)과 원격에 없는 커밋을 검사하고, 통과하면 worktree rm --run-hooks --delete-branch 를 --force 없이 불러 저장소의 archive hook 이 고유의 정리를 하게 하고(훅이 실패하면 지우지 않고 reap_blocked) 브랜치는 Orca 가 지운다. 컨테이너·볼륨·네트워크·이미지는 compose up 직후 기록한 id 만 카드가 닫힌 뒤 하나씩, 정지한 컨테이너 → 볼륨 → 네트워크 → 이미지 순으로 지운다. 쓰는 중이면 지우지 않고, 일괄 정리(prune)·down -v·라벨이나 이름 패턴 선택·base 이미지 삭제는 하지 않는다. REAPER 는 라운드마다 시각을 남기고, 오래 갱신이 없으면 멈춤 감지가 timer_stalled 로 알린다.

흐름 4. 모니터에서 깨움까지

6. 구현 순서와 전환

결론: 한 번에 짓고 한 번에 전환한다. 단계로 나누지 않고, 모듈이 무엇 위에 서는지(아래 그림)와 끄기 전에 모두 통과해야 할 검증(전환 조건)만 정하고, 통과하면 agent-skills 를 끄고 sangsoe 로 넘어간다. 구축하는 동안 일은 agent-skills 로 계속한다. 두 plugin 이 같은 일을 나눠 맡는 기간이 없어 이중 hook·이중 메시지 대기·이중 주기 실행이 필요 없다. 세부 구현 계획은 구현을 시작할 때 구현 리드가 만든다(별도 계획 문서는 없다). 전제 시험 P1–P4(Task 의존·게이트·이중 시작·다른 Run 에 묶인 세션의 쓰기)는 일회용 Run 에서 돌렸다: P1·P2(Task 상태 전환)·P4 확인, P3 부분 확인(이미 dispatched 인 Task 의 재시작 거부와 세 번 실패 차단은 첫 빌드 시험 T5 가 시작 함수에서 닫았다). 다른 Run 에 묶인 세션의 쓰기는 consumer_fenced 로 막히고 읽기는 되며, 그 Run 의 주인에게 메시지로 부탁하는 폴백이 확인됐다. Orca 에는 Run 을 닫거나 지우는 명령이 없어 시험 Run 은 남으므로 이름 접두어로 구분한다. 구현의 첫 단계가 첫 빌드 시험 T1~T6 을 돌린다(T6 은 결정 90 의 설치 길: 경로 마켓플레이스 설치와 brew upgrade 뒤 갱신 · hook PATH · Orca 개발 폴더가 앱 재시작 뒤에도 남는지): T1 worker 안 node:sqlite 열기(실패하면 sqlite 접근만 코어 프로세스를 CLI 로 부른다) · T2 worker 타이머(실패하면 orca automations --precheck) · T3 패널 그림(실패하면 상태 표시줄과 sangsoe brief 출력) · T4 승인 뒤 자율 범위와 재승인 빈도 · T5 Dispatch 재시작 거부와 세 번 실패 차단, (PR 작성자의 끝은 결정 175 가 worker_done 하나로 정했고, Orca 가 merge_ready 에 하는 일은 스모크가 잰다). 결과와 대체는 결정 84 에 있다. 돌린 결과는 시험마다 test-outcomes.md 의 행 하나다: T1–T6 모두 통과다. T5 는 Dispatch 를 가진 워커가 자기 Run 에 Task 를 만들지 못한다는 것과, Run 을 쥔 리드 세션에서 잰 이중 시작 거부(waiting already_dispatched)와 세 번 실패 차단(loop_detected 뒤 stopped start_failed_3x)을 확인했다. 거르는 것은 Orca 가 아니라 시작 함수다(결정 114).

전환 조건은 모두 통과해야 하고 하나라도 실패하면 agent-skills 를 끄지 않는다(전환 뒤에 재는 것은 없다). 검증은 전부 센 숫자로 끝나며 갈래별 개수는 기반 4 · 코어 13(스키마 불변식 허용 19 · 거부 30, 의존 실패 회귀 12/12, 결정 루프 회귀 11/11 등) · 랜드 6(land 판정 함수와 land 요청: 상주 역할 없이 함수 하나와 CLI·MCP tool) · 정리 8 · 감지기 5 · 패널 4 · 설치 3 · 이관 3, 합계 46개다.

전환은 각 PC 에서 오너가 한다: 설치 순서(2절: brew install → sangsoe install, 결정 90) → agent-skills 플러그인 비활성(지우지 않는다) → Orca plugin 승인·켜기(sangsoe plugin approve) → 열린 항목·열린 결정만 읽기 전용으로 넣기 → 시작 점검 통과·종단 실행 한 번·sangsoe todo 숫자가 패널 띠와 같음 확인. 저장소 보호 설정·CI 비밀·금지어 목록은 전환 직전에 오너가 둔다. 롤백 = agent-skills 를 다시 켜는 것이고 sangsoe 의 sqlite 는 그대로 남는다. 새로 만드는 것 13가지(일반 스킬·노트·티켓 도구·감시·정리·대시보드 등)는 agent-skills 를 참고만 하고 모두 새로 쓴다. 목록과 이유는 port-plan.md 1절에 있다.
