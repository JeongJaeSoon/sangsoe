sangsoe 소개: 여러 에이전트 세션을 한 사람이 이끄는 법

이 글은 저장소(JeongJaeSoon/sangsoe)에 있는 설계와 그 첫 빌드를 소개한다. 지금 있는 것은 사전 배포판(v0.1.0-rc.N, Homebrew 로 설치)이고 안정판은 아직 없다. 첫 빌드 시험 T0~T6(매니페스트, worker 안 sqlite, worker 타이머, 패널 그림, 승인 뒤 자율 범위, 시작 거부, 설치·갱신·재설치)은 실제 Orca 에서 돌렸고(일부 칸은 미실행) 결과는 test-outcomes.md 에 있다. 아직 돌리지 않은 것(여러 세션이 함께 도는 스모크, 시험 P5·P7 등)이 있으니, 아래 "동작한다"는 그 표에 결과가 있는 것만 확인된 것으로 읽어 주길 바란다. 확인하지 못한 부분은 6절에 따로 모았다. 설계 전체는 design.html, 세부는 design-appendix.html에 있다.

상쇠(sangsoe)는 풍물패 맨 앞에서 꽹과리 소리로 패 전체의 박자를 이끄는 사람이다. 이 프로젝트가 하는 일이 그렇다. Claude Code와 Orca에서 여러 세션에 일을 나눠 맡겼을 때, 누가 어디까지 했고 누가 막혀 있는지 놓치지 않게 하고, 필요한 쪽에만 신호를 보낸다.

그림의 색 (세 그림 모두 같은 뜻) Orca가 이미 하는 것 sangsoe 코드 (모델 없이 돈다) 모델(세션)이 맡는 것 공유 코어 · 기록 사람 · 외부

1. 왜 필요한가

세션 하나로 일할 때는 문제가 없다. 세션이 열 개, 워크트리가 열 개, PR이 열 개가 되면 사람이 기억에 의존하는 부분이 한꺼번에 터진다.

  • 워커가 오래 말이 없는데 죽은 건지 생각 중인 건지 모른다.
  • 같은 질문을 세션마다 다시 받고, 한 번 정한 결정을 다음 세션이 모른다.
  • PR이 머지됐는데 워크트리, 브랜치, 띄워 둔 Docker 컨테이너가 남는다.
  • "리뷰는 받았나, 머지는 누가 하나, 확인은 어디까지 했나"를 머릿속으로 센다.

모델에게 "기억해 두고 챙겨"라고 시키면 컨텍스트가 길어질수록 빠뜨린다. sangsoe의 접근은 반대다. 모델이 혼자 못 지키는 것은 규칙이 아니라 코드(hook, 게이트, 감지기)가 지키게 한다. 모델은 판단이 필요한 순간에만 깨어난다.

2. 한 장으로 보는 구조

sangsoe는 새 에이전트 런타임이 아니다. 세션은 Claude Code가, 터미널과 워커와 메시지는 Orca가 이미 맡고 있다. sangsoe는 그 위에 얹는 기록과 신호다. 기능은 네 칸 중 한 곳에만 둔다. 위 칸이 할 수 있으면 아래 칸에 만들지 않는다.

칸하는 일예
① Orca CLI 내장일의 원본. 항목, 의존, 게이트, 메시지, 워커 시작task-create --deps, worker-start, gate-create, send
② Orca plugin사람이 보는 화면과 모델 없는 감시패널, 상태 표시줄, monitor 5개, 정리 라운드
③ Claude Code plugin모든 Claude Code 세션에 걸리는 것위험한 행동을 막는 hook, 기록 hook, MCP 서버, skill
④ 공유 코어위 둘이 같이 쓰는 로직과 기록머지 판정, 결정 열기·닫기, 검증 등급, sqlite

두 plugin은 서로 직접 통신하지 못한다(공식 경로가 없다). 이어 주는 것은 공유 코어의 sqlite 파일과 Orca CLI뿐이다. 그래서 같은 일을 하는 입구가 늘어나지 않는다. 입구가 늘면 시험과 권한도 입구 수만큼 늘기 때문이다.

데이터는 "기능이 있는 쪽이 원본"이라는 한 줄로 정리된다. 항목, 의존, 게이트, 메시지는 Orca가 갖는다. sangsoe는 Orca id와 Orca에 없는 것(오너가 한 말, 결정 키, PR 사실, 자원 기록)만 sqlite의 event 표에 한 줄씩 덧붙인다. 고치거나 지우지 않는다. 현재 상태는 Orca를 읽은 값과 event를 합쳐 그때그때 계산하고, 합친 결과를 저장하지 않는다. 같은 사실이 두 곳에서 다른 값으로 보이는 일이 없다.

3. 일 하나가 흘러가는 모습

먼저 등장인물. 오너는 사람이다. 오케스트레이터는 오너의 말을 받는 세션이고 직접 일하지 않는다. 리드는 프로그램(관련된 일의 묶음) 하나를 맡아 워커를 시작하는 세션이다. 워커는 일 하나를 구현·조사·리뷰하는 세션이다. 이들은 서로 Orca 메시지로만 깨운다. 일의 단위는 Orca의 Task(항목)이고, 게이트는 Task를 막았다가 답이 오면 푸는 Orca 기능이다. 오너가 알아차리는 것만 따라가 본다.

① 시작. 오너가 채팅에 일을 말한다. 오너의 말은 hook이 그대로 한 줄 기록하고, 오케스트레이터 세션이 "바로 답할 것 / 읽기·조사 / 진행 중인 일의 범위 변경 / 새 일 / 시각·조건을 기다릴 일 / 오너 판단이 필요한 것" 중 하나로 분류한다. 새 일이면 항목(Orca Task)이 생기고, 프로그램 하나를 맡는 리드가 준비된 항목을 골라 워커를 시작한다. 새 워커 세션이 뜨면 SessionStart hook이 역할과 브리프 경로를 세션에 넣어 준다. 일을 시작하는 길은 이 하나뿐이라, 시작 전에 동시 실행 여유(capacity)를 먼저 확인한다.

이 길로 세션을 열지 못하면 다른 길로 열지 않는다. 예전 설계에는 Orca의 중첩 깊이 설정에 막힐 때 orca agent launch로 세션을 여는 "대체 시작"이 있었다. 그렇게 연 세션은 Orca의 배정 기록(Dispatch)이 없어서 완료 보고도, 막혔다는 보고도 위로 보낼 길이 없었다. 그래서 지금은 시작 함수가 시작을 거부하고 이유를 한 줄 남긴 뒤, 시작을 부탁한 세션이 그 일을 맡긴 쪽(리드라면 오케스트레이터, 오케스트레이터라면 오너의 할 일 목록)에 올린다. 오케스트레이터 → 리드 → 워커의 부모·자식 관계는 Orca가 기록하고, 시험이 시작한 세션마다 부모와 Dispatch가 있는지 읽어 확인한다. 깊이 설정이 낮은 Orca라면 오케스트레이터가 리드를 두지 않고 직접 워커를 연다. 모델이 이 길을 건너뛰고 터미널 명령으로 세션을 띄우려 하면(orca agent launch, 백그라운드 claude 같은 것) hook이 막고 써야 할 tool을 알려 준다. "launch agent 금지"는 macOS의 LaunchAgent도, 이 대체 시작도 둘 다 쓰지 않는다는 뜻이다.

② 감시. 일이 도는 동안 모델 없이 도는 감시자 다섯이 각자 한 가지를 본다. 타이머로 도는 코드라 토큰이 들지 않는다.

  • chat-monitor: 나에게 온 새 멘션과 내 스레드의 답글을 볼 자리. 공개 저장소에는 아무것도 읽지 않는 빈 provider 만 있다(core/detect/chat/provider.ts)
  • queue-monitor: 시작 조건이 찬 예정 항목, 오래 안 읽힌 에스컬레이션, 답은 있는데 안 풀린 결정
  • resource-monitor: 프로세스, 메모리, CPU, worktree, Docker 자원
  • orca-monitor: Orca가 아는 워커, Run, 답 없는 질문, 열린 게이트
  • pr-monitor: PR의 열림, 리뷰, CI, 머지, 검증 등급 라벨

감시자는 기록만 한다. 예외는 하나, pr-monitor가 머지 확인 뒤 PR이 걸린 항목의 Task를 completed로 닫는 것이다(⑤). 깨우는 일은 따로, 판단이 필요한 것에 한해 Orca 메시지 한 통으로 한다.

③ 멈춤 감지. 워커가 오래 조용하면 orca-monitor가 Orca가 알려 주는 마지막 출력·활동 시각으로 판정한다(그 필드의 뜻은 6절). 멈췄다고 보면 워커, 그 일을 쥔 리드, 오케스트레이터 순서로 한 번씩 깨운다. 같은 세션을 두 번 깨우지 않고, 깨웠는데 읽히지 않으면 한 단계 위로 올린다. 위로 올라가도 풀리지 않는 것, 곧 오너만 답할 수 있는 질문은 결정(🙋)으로 열린다. 한 번 답한 결정은 닫히고, 같은 질문은 다시 만들어지지 않는다. 기다리던 워커에게는 답이 Orca 메시지로 간다.

④ PR과 확인. 워커가 PR을 열고 독립 리뷰에서 더 고칠 것이 없으면 sangsoe land(MCP tool로도 부른다)를 부른다. 이 함수가 먼저 검증 등급이 요구하는 증거가 머지할 커밋에 있는지 본다(아래 5절 표). 없으면 거부한다. 통과하면 저장소 설정이 자동 머지 조건 네 가지를 모두 만족할 때만 머지를 예약한다. 하나라도 거짓이면 예약하지 않고 "승인되면 머지"로 남긴다. 작성자 말고는 승인할 계정이 없는 저장소는 설정으로 켜면, 기록된 독립 리뷰 판정과 초록 검사를 승인 대신 세어 바로 머지한다(결정 158). 작성자는 어느 쪽이든 보고하고 스스로 끝난다. 머지하는 길은 이 하나뿐이다.

⑤ 머지 확인. 머지 뒤에 pr-monitor가 GitHub이 머지로 표시했는지, 머지 커밋이 main에 들어갔는지를 둘 다 읽는다. 둘 다 참일 때만 pr-monitor가 그 Task를 completed로 닫고, 항목이 ✅ 완료가 된다. 증거 없이 닫힌 항목은 🔍로 표시되어 리드가 다시 본다. main의 CI가 빨개지면 🚨와 함께 다른 PR의 머지를 막는다.

⑥ 정리(REAPER). 끝난 일이 남긴 worktree, 브랜치, Docker 자원을 치우는 라운드다. 먼저 후보를 표시하고, 조건을 만족한 것만 정리한다.

  • 열린 PR이나 닫히지 않은 항목이 가리키지 않아야 한다.
  • "끝났다"는 판정이 긍정이어야 한다(PR이 머지되었거나 닫혀서 HEAD가 실렸거나, 항목이 완료·취소됨). "조용하다"는 이유로는 지우지 않는다.
  • 서로 다른 두 라운드에서 연속으로 후보였고 유예 시간이 지났어야 한다.
  • 삭제 전에 커밋 안 된 변경과 원격에 없는 커밋을 검사한다. 통과하면 Orca의 worktree rm을 강제 옵션 없이 부르고, 저장소의 orca.yaml에 둔 archive hook이 먼저 돌아 그 저장소만의 정리(예: 자기 compose 내리기)를 한다. 훅이 실패하면 아무것도 지우지 않고 사람에게 넘긴다.
  • 모르는 것은 지우지 않는다. 기록하지 않은 Docker 자원은 알리기만 한다.

⑦ 오너가 보는 것. 오너는 Orca 메시지를 직접 받지 않는다. Orca 패널(오른쪽 사이드바)과 상태 표시줄로 본다. 화면 구성은 5절에서 다룬다.

4. 직접 만들지 않고 가져다 쓴 것

가장 중요한 원칙은 하나다. Orca나 Claude Code가 이미 하는 일은 만들지 않는다. 판정 순서는 Orca 기능, Claude Code 기본 기능, 자체 스크립트 순이다. 자체 상주 프로세스, 포트, 웹 서버는 없다. 웹 대시보드도 없다.

sangsoe가 직접 만들던 것을 Orca의 hook과 내장 기능이 대신할 수 있는지, 후보 23개를 하나씩 따져 봤다(그 조사 메모는 이 저장소에 없고, 결론은 design.html 의 Orca 기능 표에 있다). 결과는 "그대로 쓴다" 11, "틈만 메운다" 6, "쓰지 않는다" 6이다. 대표 사례만 적는다.

  • 그대로 쓴다: 저장소의 archive hook(위 정리 단계), worktree 목록의 isMainWorktree 필드(메인 체크아웃을 건드리지 않으려고), worktree rm --delete-branch(머지를 증명한 브랜치만 지움), 워커 터미널 자동 해제. 일부(재시도 체인과 세 번 실패 차단)는 도움말로만 확인했고 실행 확인 전이다. /goal 입력의 제출 확인도 "그대로 쓴다"였지만, 그것을 쓰던 대체 시작이 없어져 지금은 쓰지 않는다.
  • 틈만 메운다: 워커 활동 시각 필드(값의 뜻은 아직 재 봐야 한다), 메시지 재전송(같은 사람을 두 번 깨우지 않는 중복 방지는 Orca에 없어서 남긴다).
  • 쓰지 않는다: Orca의 plugin hook으로 게이트를 옮기는 안은 버렸다. 그 hook은 SSH·WSL의 세션에 걸리지 않고 세션 id도 주지 않아서, "모든 Claude Code 세션에 걸려야 한다"는 게이트의 조건을 못 채운다. 그래서 게이트는 Claude Code의 command hook에 둔다. (게이트 = 조건이 안 맞으면 행동을 막는 hook)

같은 이유로 일을 기다리는 곳도 한 군데다. 지금 돌고 있지 않은 일은 Orca Task(예정·준비됨·막힘)와 열린 Orca 게이트로만 기다린다. 파일 큐도, 채팅 속 약속도 없다.

Jira나 Linear 같은 외부 티켓도 같은 방식으로 다룬다. 일의 기록은 Orca Task 하나이고, 티켓은 일을 하는 워크스페이스에 orca reference add로 키와 주소만 붙인다. 복사하거나 동기화하지 않고, sangsoe는 트래커에 아무것도 쓰지 않는다. 티켓 상태를 옮기는 일은 오너가 쓰는 트래커 도구가 붙어 있는 참조를 읽어서 한다. 아직 워크스페이스가 없는 예정 항목은 Task의 제목이나 본문에 티켓 키를 적어 두고, 워커를 시작해 워크스페이스가 생기면 그때 붙인다.

5. 매일 쓰는 법

설치

지금은 사전 배포판(v0.1.0-rc.N)만 있다. 아래 절차는 저장소 README.md 의 Install · Update · Uninstall 과 같다.

설치 길은 하나다. Homebrew가 코어와 매니페스트 둘(.claude-plugin/plugin.json과 orca-plugin.json)이 든 트리 하나를 깔고, sangsoe install이 그 트리를 각 호스트의 공식 명령으로 Claude Code plugin과 Orca plugin에 등록한다(결정 90·108). 필요한 것은 macOS 의 Homebrew, Claude Code, Orca, 인증된 gh 다. 사람이 순서대로 실행한다.

  1. brew install JeongJaeSoon/tap/sangsoe 다음 sangsoe --version. sangsoe <버전> 을 출력한다.
  2. sangsoe install: 두 plugin 을 등록하고 sangsoe doctor 를 돌린다. 다시 불러도 된다. 처음에는 claude: added marketplace sangsoe → …/libexec · claude: installed sangsoe@sangsoe · orca: loaded, approval waits — fingerprint ap1-…; next: sangsoe plugin approve 를 출력한다. 뒤따르는 doctor 행에서 FAIL orca plugin: local.sangsoe waits for approval 은 예상된 것이고 warn orca-plugin-version 이 함께 나올 수 있다. 둘 다 고칠 명령으로 sangsoe plugin approve 를 적는다.
  3. sangsoe plugin approve: 세 가지가 참일 때만 Orca plugin 을 켠다. 그 빌드의 PR 이 Act-on 0 인 독립 리뷰를 받았고 이 머신에 sangsoe review record --pr <n> --head <sha 40자> --act-on 0 --reviewer <이름> 로 기록돼 있을 것(결정 111), 설치된 폴더의 내용이 빌드 커밋과 리뷰된 head 둘 다와 같을 것(결정 105), Orca 가 이 폴더의 local.sangsoe 를 정확히 물을 것. 먼저 --dry-run 으로 각 검사와 부를 orca plugin enable 명령을 본다. 성공하면 recorded plugin_approved (seq N) 와 enabled 를 출력한다.
  4. sangsoe doctor 가 모든 행에 ok 를 내고 0 으로 끝난다. 예외는 reaper-config 의 notice 행 하나다: 설정 파일에 reaper 칸이 없으면 REAPER 는 표시만 하고 정리하지 않는다(결정 153). sangsoe install 은 이 칸을 쓰지 않는다.

갱신. brew upgrade sangsoe → sangsoe install → 새 빌드의 리뷰 기록(sangsoe review record) → sangsoe plugin approve → sangsoe doctor. 버전마다 Cellar 폴더가 따로이고 Orca 가 승인을 그 폴더에 묶으므로(결정 122), 갱신할 때마다 새 리뷰 기록과 새 승인이 든다. 이전 버전의 기록은 이어지지 않는다. 승인은 Orca plugin 이 돌리는 코어까지 덮는다: 릴리스가 core/ 사본을 orca-plugin/vendor/ 에 싣고 plugin 은 그 사본만 연다(결정 152). 같은 버전을 다시 까는 것(brew reinstall sangsoe 뒤 sangsoe install)은 새 승인이 필요 없다.

제거. sangsoe uninstall 다음 brew uninstall sangsoe. 어느 쪽도 데이터(~/.local/share/sangsoe)와 설정(~/.config/sangsoe)을 지우지 않는다.

오너는 permissions.allow에 sangsoe plugin approve 한 줄만 넣는다. orca plugin enable 자체는 넣지 않는다. 그래야 에이전트가 다른 plugin을 승인하거나 조건을 우회하지 못한다.

자주 부르는 것

오너는 대부분 말로 한다. 자주 쓰는 명령은 몇 개뿐이다.

명령누가하는 일
sangsoe brief [묶음] [항목]오너현황을 세 단계(묶음 → 묶음 상세 → 항목 상세)로 본다
sangsoe todo오너내가 할 일만 모아 본다
sangsoe land --pr <N>워커, 리드증거를 점검하고 머지를 예약하거나 "승인되면 머지"로 남긴다
sangsoe recover오너, 리드머신 재시작 뒤 Orca 의 워커를 Task · Dispatch · 상태 · liveness · 터미널 · worktree 표로 보고 잃었을 수 있는 워커를 표시한다. 읽기 전용이다
sangsoe verify-tier --pr <N>누구나PR의 검증 등급을 계산해 본다

에이전트(오케스트레이터, 리드, 워커)는 Bash로 CLI를 부르지 않고 MCP tool만 쓴다. 인자의 타입이 정해져 있고, 거부 오류가 글자가 아니라 구조로 오기 때문이다. 쓰는 tool은 열네 개다. 항목 만들기, 의존 더하기·빼기·펼치기, 결정 열기·답하기, 세션 시작이 일곱 개의 행동이고, 여기에 land 요청 하나와 기록 여섯(인계 저장, 리뷰 의뢰 기록, 리뷰 판정 기록, 만든 자원 기록, 검증 증거 기록, 배포 단계 기록)이 더해진다. 상태 전환은 Orca 의 Task 명령을 그대로 쓴다(결정 160). 읽기는 tool이 아니라 resource 넷(현황 1단계, 시작할 수 있는 항목, 모델 선택 표, 항목 이력)으로 열린다. CLI는 MCP를 못 쓰는 호출자(hook, 사람 터미널, CI)용으로 얇게만 둔다.

패널이 보여 주는 것

패널은 읽는 도구이고, 같은 모델을 sangsoe brief도 쓴다.

  1. 현황: 맨 위에 ✅ 완료 · 🔄 진행 중 · 남은 것 · 🚧 막힌 것 건수 한 줄, 그 아래 표 네 절(결정 필요 · 지금 오너가 할 일 · 진행 중 · 보류). 리드, 카드, PR, 워커가 한 행씩이다. 오너가 해야 하는 행은 배경색 없이 🚧 마커와 절 건수로 가리키고, 표 행은 모두 같은 높이다.
  2. 묶음 상세: 항목, 세션, PR을 상태별로 한 줄씩. 선행 → 후속은 SVG 그림으로, 크리티컬 패스는 번호로 보이고, 아직 못 시작한 일은 "왜 준비되지 않았나" 표가 막는 선행과 해야 할 일을 보여 준다. 넓은 화면은 왼쪽에 그래프와 그 아래 간선 범례, 오른쪽에 같은 높이의 표 넷(더 길면 안에서 스크롤)이고, 360px 은 그래프, 범례, 표 순으로 쌓인다.
  3. 항목 상세: 오너가 한 말에서 시작해 분류, 전환, 증거, 연결된 PR과 결정까지.

패널 맨 위에는 Orca 자신의 패널처럼 머리 행(새로 고침 · 터미널에서 전체 현황 · 더 보기)과 전체 · 할 일 · 진행 중 탭이 있고, 비어 있는 절은 한 줄로 접힌다. Orca 상태 표시줄에는 이름표와 같은 건수의 짧은 꼴(✨ SANGSOE 🚧 2 · 결정 2 · 🔄 5)이 뜨고, 오너가 할 일이 있으면 붉게 바뀐다.

상태는 📅 예정 · 🟢 준비됨 · 🔄 진행 중 · 🚧 막힘(누가 막는지 괄호에 적는다) · ⏸️ 보류 · ✅ 완료 · 🗑️ 취소, 플래그는 🙋 결정 필요 · 🚨 오류·멈춤 · 🔍 근거 부족이다. 이모지는 이 뜻 외에는 쓰지 않는다. 패널, 상태 표시줄, sangsoe todo의 "내가 할 일" 숫자는 같은 계산에서 나오므로 어디서 봐도 같다.

오너가 직접 해야 하는 것

  • 결정(🙋)에 답하기. 채팅이든 패널 버튼이든 오너의 말은 같은 기록이 된다. d012처럼 결정 번호를 붙여 답하면 바로 이어지고, 번호 없이 "빨간색으로 하자"만 쓰면 오케스트레이터가 어느 결정의 답인지 잇는다. 애매하면 한 번 되묻는다.
  • plugin 승인. 릴리스마다 한 번.
  • prod 단계와 사람 승인이 필요한 머지. 이 단계들은 시작하는 쪽이 오너이고 "내가 할 일"에 올라온다.
  • 설정. 문서·테스트·화면 경로 목록(docs_globs, test_globs, ui_globs), 보호 경로(protected_paths), 등급을 내릴 수 있는 사람(owners), 감시할 저장소 범위(watch) 같은 값은 설정 파일에 둔다. 채널이나 사람 이름 같은 사내 값도 코드가 아니라 ~/.config/sangsoe/에 둔다.

큐는 어떻게 스스로 닫히나

오너 앞에 쌓인 것(결정, 오너가 할 일, 권한 대기)은 관측한 사실 아니면 기록된 답으로만 닫힌다. 오너가 터미널에 무엇을 쳤다는 것만으로는 닫히지 않는다. 입력은 "이 일에 대한 것일 수 있다"는 단서일 뿐이어서, 항목에는 입력 확인됨 · 검증 중 표지만 붙고 상태는 그대로다. 명령은 실패해도 쳐지고, 비슷한 다른 명령을 쳤을 수도 있고, "했다"고 적고 안 했을 수도 있기 때문이다.

일은 세 층이 나눠 한다.

  • 감지 (hook과 monitor, 토큰 없음): 사실과 표지만 쓴다. 오너의 말, 증거, 권한 대기가 풀렸다는 관측(세션이 다시 움직임), 검증이 참이라는 닫기 제안. 항목은 닫지 않는다.
  • 실행 (코어 함수와 패널 버튼): d012처럼 번호를 붙인 답이나 패널 버튼처럼 어느 항목의 답인지 명시된 것만 처리한다. 결정의 게이트를 풀고, 패널의 "완료" 버튼으로 오너 항목을 닫는다.
  • 판단 (리드, 오케스트레이터): 닫기 제안과 증거를 보고, 완료 버튼을 누를 항목이라고 오너에게 알린다. 오너 항목은 오너가 닫는다(결정 162).

오너가 할 일에는 선택적으로 "끝났다는 걸 기계가 읽는 조건"(머지됨, 워크플로 실행 성공, PR 존재, plugin 승인 등)을 달 수 있다. 이 조건이 참이 되면 오너가 채팅 한 줄 쓰지 않아도 할 일에서 사라지고 리드에게 닫기 제안이 간다. 조건이 없는 항목은 "검증 없음"으로 보이고 패널 버튼이 답이 된다. 원인이 사라진 결정(막던 작업이 닫힘, PR이 닫힘)은 답 없이 닫히고, 뒤늦게 온 답은 기록만 된다. 오너 입력 하나로는 어떤 항목도 답한 것으로 치지 않는다.

검증 등급

PR마다 변경 내용을 보고 등급을 매기고, 등급에 따라 머지 전에 요구하는 증거의 깊이를 달리한다. 등급은 코드(토큰 없음)가 base...head diff의 경로와 변경 종류, 라벨로 계산한다. 판정이 애매하면 높은 쪽으로 올린다.

등급대상머지 전에 필요한 증거
V0문서, 주석만 바뀜필수 CI 통과
V1테스트만, 또는 리팩터V0 + 대상 테스트 실행 출력
V2로직 변경V1 + 변경한 동작을 실제로 돌린 출력(무엇을 확인했고 무엇을 확인하지 못했는지까지)
V3화면, 외부 연동, 배포, prod, 보안, 의존성V2 + 화면이면 스크린샷·GIF, 배포·연동이면 dev 반영 확인, 사람 승인

모든 증거는 "머지할 그 커밋" 기준이다. 새 push로 커밋이 바뀌면 이전 증거는 무효가 된다. 사람이 verify-tier:N 라벨로 등급을 바꿀 수 있는데, 올리기는 누구나 되고 내리기는 owners가 단 것만 유효하다. 보호 경로를 건드린 PR은 어떤 라벨로도 V3 아래로 못 내린다. 한 가지 더. 머지가 배포를 일으키는 항목은 V0 PR이라도 dev 확인 증거가 없으면 ✅가 되지 못한다.

6. 범위와 한계

범위. PC 한 대마다 sangsoe가 하나씩 돈다. 각 sangsoe는 자기 PC의 로컬 worktree만 읽고 쓰고, sqlite 파일(~/.local/share/sangsoe/sangsoe.db)도 PC마다 따로 둔다. 이 파일을 PC 사이에 동기화하면 안 된다(WAL 모드가 네트워크 파일시스템에서 깨진다). 다른 PC에서 일을 시키려면 Orca의 relay로 그 PC에 닿고, 거기서는 그 PC의 sangsoe가 자기 worktree를 맡는다. 한 sangsoe가 원격 호스트의 worktree까지 건드리는 설계는 하지 않는다. 이유가 있다. 원격 행에서는 로컬 git과 포트 조회가 틀리게 읽히고, 게이트도 그 호스트의 Claude Code에 plugin이 설치돼 있어야만 걸리기 때문이다. 이 범위는 오너가 2026-11-09에 정한 결정이다(결정 88). 코어는 Orca 행의 hostId가 local인 것만 후보·대상·판정에 쓰고, 나머지는 지우지도 멈춘 것으로 보지도 않으며 remote_host라는 사유로 남기기만 한다. 시작 점검은 그런 행이 보이면 "건드리지 않는다"는 경고를 한 줄 낸다. 첫 빌드는 relay를 연결한 채 다른 PC의 행이 어떻게 보이고 이 필터가 지켜지는지를 시험한다(시험 P11). 조사 메모(_research/remote-env-impact.md)는 원격 행에서 틀리게 동작할 곳을 한 군데로 좁혔고, 그 한 군데가 이 필터로 닫힌다.

첫 빌드가 잰 것. 설계가 "구현 전에 재 봐야 할 것"으로 남긴 목록은 첫 빌드가 먼저 시험했다. 결과와 명령, 출력 발췌는 test-outcomes.md 의 행 하나씩에 있다.

  • Orca plugin worker 안에서 node:sqlite가 열린다 (T1 통과, 대체 없음)
  • worker 타이머가 정해진 간격으로 감시자를 돌린다 (T2 통과. Orca 자동화의 --precheck 대체는 쓰지 않는다)
  • 패널이 Orca 안에서 그려진다 (T3 통과)
  • 승인 뒤 worker 가 자율로 돌고, 재승인은 능력·명령·실행 단계가 바뀔 때만 든다 (T4 통과)
  • Dispatch 를 가진 워커는 자기 Run 에 Task 를 만들 수 없다. 이중 시작 거부와 세 번 실패 차단은 미실행이라 시작 함수가 스스로 거른다 (T5, 결정 114)
  • --force 없는 worktree rm 은 더러운 worktree 를 지우지 않지만 푸시 안 된 커밋은 막지 않아, REAPER 가 먼저 검사한다. archive hook 의 동작은 미실행 (P6 부분 통과)
  • 활동 시각 필드는 일하는 세션에서 움직이지 않아, 멈춤 판정은 마지막 출력 시각을 쓴다 (P10)

아직 돌리지 않은 것: 여러 세션이 함께 도는 스모크, 라벨 이벤트의 지연과 실제 PR 로 돌려 본 등급 분포, 그리고 같은 표에 "미실행"으로 남은 행. 기존 도구(agent-skills)는 전환 조건 46개(switch-conditions.md)가 모두 통과한 뒤에야 끈다. 그 표에 증거가 빈 줄이 아직 있다.
