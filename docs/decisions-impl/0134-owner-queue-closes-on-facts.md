# 134. 오너 큐는 관측한 사실과 기록된 답으로만 닫는다: `owner_todo` 몸체 · 표지 · 입력 연결

결정 12·37·49·89·91·92⑥ 을 `core/owner/` 로 옮기며 정한 것이다.

- **`owner_todo` 몸체는 하나.** `ownerTodoFrom(input, facts)` 가 네 종류(열린 결정 · 오너가 who 인 🟢 · 리드가 못 푼 `waiting_human` · 전달되지 않은 답)를 만든다. `facts` 는 좁은 구조 타입 `OwnerItemFacts`(task · alias · state · who · execBy · whyOwner · since · closedAt)이고 U9 의 `ItemFacts` 가 그대로 맞는다. 그래서 현황 표·`sangsoe todo`·이 모듈이 항목을 한 번 접어 한 번 센다(PN3). `core/brief/owner_todo.ts` 는 이 함수에 넘기기만 한다.
- **빠지는 길은 관측 사실뿐.** 오너 항목은 그 항목의 `verify` kind 와 같은 `evidence{probe:<kind>}` 가 항목 생성 뒤에 있으면 빠진다(진행 중 절의 🟢 로, 결정 37 과 같은 자리). `waiting_human` 은 `waiting_released` 로 빠진다. 결정과 답은 U8 의 `decision` 뷰가 정한다. 채팅 한 줄이 쓰는 `owner_action` 은 어느 판정에도 들어가지 않는다(시험 "no chat line alone…").
- **오케스트레이터 시작 거부(U10 의 LATER).** 결정 94 (다)·용어집 "시작 거부" 는 `escalation{to: owner}` 가 `owner_todo` 로 간다고 하고, 결정 89·용어집 "오너 할 일" 은 네 종류만 센다. 둘을 이렇게 맞춘다: 그 거부는 거부된 Task 의 항목 행 하나(`kind: owner_item`, `whyOwner: start_refused:<reason>`)이고 다섯째 종류를 만들지 않는다. Orca 가 그 Task 를 `pending`·`ready` 밖(시작됨·완료·실패)으로 보이면 빠진다(관측 사실). `entity_id` 가 항목이 아닌 worktree 인 거부는 접을 행이 없어 세지 않는다(발견으로 보고). 같은 항목이 오너 항목이기도 하면 한 행이다. 구현 결정 128 의 "세지 않는다" 를 이 규칙이 대체한다. 그 골든 시험의 거부는 항목이 없는 Task 를 가리켜 여전히 행이 없다.
- **표지는 상태가 아니다.** `ownerMarks` 가 event 에서 접는다: `owner_act:seen` → `verify` 가 있으면 `입력 확인됨 · 검증 중`(verifying), 없으면 `검증 안 됨`(no_verify) · `owner_act:failed` → `실행 실패`(표지가 없을 때만) · 오케스트레이터의 `owner_class{not_yet|cancel}`(항목에 `entity`) → 표지와 `run` 을 비움 · verifying 이 `verify.wait_minutes` 를 넘고 probe 가 참이 아니면 `검증 안 됨`(unverified, 뷰가 시각으로 계산하고 event 는 없다). 표지는 `owner_todo` 의 행 수·네 버킷에 들지 않는다.
- **전이표의 "상태가 바뀌는 행은 1·2·8·9·10".** 8(같은 명령 다시: `run` 만 바뀜)과 10(아직: 표지를 뗌)은 결정 본문이 "상태는 그대로" 라고 쓴다. 그래서 그 문장의 "바뀜" 을 "기록된 무엇이 바뀜" 으로 읽는다: 1·2 는 항목 상태(명시적 연결), 9 는 `owner_todo` 행과 `close_suggested`(관측 효과), 8·10 은 표지의 칸. 나머지 3–7·11 은 상태도 `owner_todo` 의 수도 바꾸지 않는다(5·6·7·11 은 표지만). `test/owner/transition-table.test.ts` 가 11행을 이 구분으로 고정한다.
- **🔍 를 푸는 증거.** `countsAsEvidence` 는 `owner_act:*`(오너의 `!` 줄 · 제안) 를 뺀 `evidence` 를 센다: `probe:*` · 버튼의 `owner_done` · land 의 `test`·`run` 등. `owner_act:*` 는 입력이라 세지 않는다. U9 의 `evidenceShort` 가 이 술어를 부른다(전에는 항목에 붙은 어떤 `evidence` 든 🔍 를 풀어, 오너가 `!` 한 줄을 치고 완료를 누르면 probe 없이 🔍 가 사라졌다).
- **입력 연결(`linkShell`).** 열린 🟢 오너 항목 가운데 (i) `cmd_hint` 의 모든 조각이 명령의 토큰에 있거나 (ii) `verify.pr` 의 PR URL 이 명령에 있고, 저장소가 같으며(명령의 `-R`/`--repo`, 없으면 세션 저장소; 항목 저장소는 `verify` 의 `repo`/`pr`), 항목 생성 시각이 입력보다 앞선 것이 정확히 하나일 때만 잇는다. 종료 코드≠0 이나 stderr 가 있으면 `owner_act:failed`, 종료 코드를 모르면(P13) `run_ok` 항목에서 stdout 에 그 저장소의 run URL 이 있을 때만 잇는다. 하나도 안 맞거나 둘 이상이면, 감시 명령이면 `owner_act_unlinked`, 아니면 아무것도 쓰지 않는다. `run` 칸은 stdout 의 `/actions/runs/<id>` 에서 채운다. 채팅(`linkChat`)은 `dNNN` 만 명시적 연결이고 `iNNN` 만 있으면 제안(`owner_act:proposed`)뿐이다.
- **`dedupe_key`.** 접두어는 type 의 것이라(`core/contract/dedupe.ts`) 결정 91 의 `owner_act:<uuid>` 는 `evidence:owner_act:<uuid>` 와 `owner_act_unlinked:owner_act:<uuid>` 로 적는다. 한 transcript 줄은 둘 중 한 줄만 남긴다. probe 는 `evidence:probe:<task>:<kind>`, 닫기 제안은 `close_suggested:<task>:verified`, 검증 미확인 escalation 은 `escalation_stale:<task>:verify_unconfirmed:<표지 seq>`(표지마다 한 번)다. 이 단위와 함께 들어온 U13 의 hook(`core/session/`, 구현 결정 131)은 이 두 함수를 부르지 않고 같은 이벤트를 다른 키(`evidence:<uuid>:owner_act`)와 다른 규칙으로 직접 쓴다. 이 모듈의 읽는 쪽(`ownerMarks`·`owner_todo`·현황)은 그 이벤트를 그대로 읽는다. 쓰는 규칙을 한 곳으로 모으는 일은 발견으로 넘긴다.
- **연결 안 된 행동의 연결(결정 91⑤).** `decision_answered` 에 `ref` 칸이 없어, 오케스트레이터가 이을 때는 `decision_answered`(또는 항목에 단 `evidence`)의 `subject` 칸에 `act:<seq>` 를 적는다. `linkedActs(events)` 가 그 seq 들을 돌려주고, 현황의 PR 행은 그 즉시 빠진다. 계약 칸은 늘리지 않았다(발견으로 보고).
- **`verify` 는 항목당 하나.** 계약의 `item_extra_set.verify` 가 kind 하나라 결정 91 9행의 `run_ok`+`pr_found` 둘을 함께 걸 수 없다. 시험은 kind 마다 따로 본다(발견으로 보고: 계약 `verify` 를 목록으로).
