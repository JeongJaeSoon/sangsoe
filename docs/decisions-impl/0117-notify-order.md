# 117. `notify` 가 지키는 받는 순서와 한 번

결정 76(5)·80 N8 과 부록 `#delivery` 를 함수 하나로 옮기며 정한 것이다.

- **입력은 id 만.** 부르는 쪽은 받는 사람들(`dispatch` = 일을 쥔 워커, `leadRun` = 소유 리드의 Run, `orchestratorRun`)과 보낼 사람(`to`)을 준다. 주소는 `notify` 가 `dispatch:<id>`·`run:<id>` 로 만든다. `term_` 로 시작하는 id, `:`·공백이 든 값(이미 만든 주소)은 거부한다.
- **순서.** 받는 사람 셋 가운데 주어진 사람만 순서에 든다(없거나 죽은 사람은 부르는 쪽이 빼고 준다). 아직 아무도 받지 않은 조건은 맨 앞 사람에게만 보내고 기본 키를 쓴다. 이미 누가 받은 조건은 `escalate` 일 때만 위로 올리고, 받은 사람 가운데 가장 높은 사람 바로 다음(그 사이에 주어진 사람이 있으면 `out_of_order`)에게 보내며 키 끝에 받는 쪽 이름을 붙인다. `escalate` 가 없으면 `already` 다. 누가 받았는지는 부르는 쪽이 준 사슬이 아니라 기록된 줄(접미어, 기본 줄은 `to` 주소)로 읽으므로, 워커가 받은 뒤 죽어 사슬에서 빠져도 리드를 건너뛸 수 없다. 오너는 순서에 없다.
- **한 번.** 보내기 전에 같은 키의 `notified` 를 찾고 있으면 보내지 않는다. 보낸 뒤 `notified` 를 쓴다. 응답을 잃은 보내기(`response_lost`)는 다시 보내지 않는다: Orca 가 요청 id 를 알려 줬으면 같은 호출 안에서 `recoverWrite` 로 `request-show` 를 본 뒤 같은 id 로만 다시 보내고(결정 60), id 가 없거나 회복이 안 되면 도착했을 수 있으므로 `msg_id = undetermined:<id|none>` 로 줄을 쓰고 `send_undetermined` 로 거부한다. 다음 호출은 `already` 다. 남는 창은 하나다: 보내기가 성공하고 줄을 쓰기 전에 죽거나, 두 호출이 같은 조건을 동시에 보내면 한 번 더 갈 수 있다(적어도 한 번). 부록 `#delivery` 가 "보내고 나서 적는다" 순서를 정했고, 요청 id 는 보낸 뒤에야 생기므로 미리 적을 수 없다.
- **`msg_id`.** `send` 영수증에서 메시지 id 를 찾고, 없으면 요청 id, 그것도 없으면 `unrecorded` 를 적는다. 영수증 모양은 아직 실측되지 않았다.
- **기본 줄의 받는 쪽은 주소로 읽는다.** 기본 키 줄이 오케스트레이터에게 간 것인지는 이번 호출의 `orchestratorRun` 과 `to` 를 맞춰 본다. 이번 호출이 `orchestratorRun` 을 빼면 리드로 읽힌다(검토 2회차 C4, 남겨 둠: 줄에 받는 쪽을 적으려면 `notified` 계약을 바꿔야 한다).
- **모아 보내기(부록 `#delivery`, 기본 300초)는 이번에 만들지 않았다.** 결정 루프의 보내기는 모두 즉시 깨움 쪽(답·막힘 해제)이다.
