# 브리프 쓰기

브리프는 새 세션이 가진 유일한 맥락이다. 받는 쪽은 너의 대화를 보지 못한다. 그래서 브리프는 "무엇이 끝인가"를 받는 쪽이 혼자 판정할 수 있게 쓴다. 모양(필수 칸, 형식)은 tool 이 검사한다. 여기서는 무엇을 쓰는지만 정한다.

## 칸

코어가 첫 줄에 역할 줄(`sangsoe-role: …`)을 붙인다. 브리프는 그다음 줄부터다. 역할 줄을 직접 쓰지 않는다.

| 칸 | 쓰는 것 |
|---|---|
| 목표 | 한 문장. 무엇을 바꾸거나 알아내는가 |
| 완료 조건 | 받는 쪽이 실행해서 확인할 수 있는 조건 목록. 조건마다 확인하는 명령이나 관찰을 붙인다. "잘 동작한다"는 조건이 아니다 |
| 범위 | 고쳐도 되는 경로와 고치면 안 되는 것. 임시 파일을 둘 곳. 남기는 checkout·등록·브랜치·파일·프로세스는 `resource_record` 로 기록하라는 줄(smoke·릴리스 단위에서 특히, 결정 240) |
| 맥락 | 읽어야 할 문서·결정 번호·관련 PR. 결론이 아니라 근거를 가리킨다 |
| 검증 | 어떤 증거가 필요한가. 머지가 걸린 일이면 검증 등급(V0–V3)이 정하는 증거. 확인 명령은 그대로 적는다. 증거는 리드가 `evidence_record` 로 기록하고, 워커는 실행 출력과 확인 못 한 것을 리드에게 보낸다(결정 171) |
| 계보 | 받는 쪽이 리드면, 단위의 세션은 MCP tool `start_unit` 으로만 연다(Task 없는 리드도, 결정 243). 받는 쪽이 워커면 이 칸 대신 아래의 "워커는 세션을 시작하지 않는다" 줄을 둔다 |
| 머지 | 리뷰 판정은 작성자가 아니라 리드가 `review_record` 로 기록한다(결정 111). 워커는 리뷰한 head·리뷰어·리뷰 원문의 위치를 리드에게 보낸다. 머지는 `land` tool 하나이고, 끝은 `merge_ready` 를 담은 worker_done 이다. 리드의 go 뒤에 머지하는 단위면 그 조건, go 뒤에 누가 `land` 를 부르는지, go 전에 보내는 worker_done 본문에 `READY-WAIT: <kind>` 줄을 둔다는 것을 여기 적는다. 그 줄이 없으면 `[gate:self-land]` 가 열린 PR 위의 worker_done 을 막는다(결정 201) |
| 승인 줄 | 오너의 말을 그대로 인용한 줄: `오너(dNNN, 날짜): "원문"`. 이 줄 밖의 일은 escalation 이다 |
| 보고 | 끝은 worker_done 한 번. 본문에 담을 것(바꾼 것, 증거, 확인 못 한 것, NOW·LATER·DROP 제안). 도중의 메시지는 다음 걸음으로 type 을 고른다: 답을 기다릴 메시지는 question 이다(워커는 `ask`), 답을 기다리지 않는 보고만 status 다 |
| 거부 | 아래 거부 문단을 그대로 붙인다 |

## 첫 프롬프트에 대해 알아둘 것

- Orca 는 워커의 첫 프롬프트를 자기 문구로 감싸 붙인다. 그래서 브리프 안의 `/goal` 줄은 워커·리드에게 걸리지 않는다. 끝나는 조건은 Dispatch 와 worker_done 이다. 완료 조건을 `/goal` 에 기대지 말고 본문에 쓴다.
- 워커는 세션을 시작하지 않는다. 브리프에 "도우미 워커를 띄워라"를 쓰지 않는다. 손이 더 필요하면 읽기 전용 서브에이전트나 리드에게 묻는 것이다.
- 보고 주소는 Run·Dispatch 다. 터미널 핸들(`term_…`)을 주소로 쓰지 않는다. 핸들은 재시작마다 바뀐다.
- 앞 워커가 끝난 뒤 도착한 답은 브리프에 섞지 않고 `start_unit` 의 `lateAnswers` 로 넘긴다.
- 모델 이름·effort 를 브리프에 적지 않는다. 단위의 종류는 `item_create`·`start_unit` 의 `class`(`default`·`hard`·`design`·`mechanical`·`docs`)로 표시한다(결정 187, 200). 브리프 본문에는 왜 그 class 인지 한 줄만 적는다. 문서만 바꾸는 단위는 `docs` 다.
- 워커가 advisor 를 언제 부르는지와 몇 번인지 한 줄 적는다: 접근을 정하기 전, 막혔을 때, 끝났다고 말하기 전, 행의 예산(resource `models` 의 `budget`) 안에서. 매 턴이 아니다. 예산 0 인 행과 예산을 다 쓴 단위는 advisor 가 꺼진 채 시작한다(결정 202).
- 행의 effort 가 high 아래면(resource `models` 로 본다) 완료 조건 앞에 한 줄을 넣는다: "일 전체를 끝까지 한다. 남은 일 목록이나 계속할지 묻는 말로 턴을 닫지 않고, 평범한 장애는 진단해 넘어간다." SessionStart 도 같은 줄을 주지만, 브리프가 받는 쪽의 유일한 맥락이므로 본문에도 둔다.
- 서브에이전트를 쓰라고 할 때는 그 `model` 을 resource `models` 의 `subagents` 로 정하라고 적는다(결정 188).

## 서브에이전트 지시문

브리프가 서브에이전트를 쓰게 하면, 그 지시문에 아래 두 줄을 넣으라고 적는다. 리드·오케스트레이터가 직접 쓰는 서브에이전트 지시문에도 넣는다.

- 하네스가 저장한 파일(tool-results, 백그라운드 task 출력)은 Read tool 로만 읽는다. 작업 폴더 밖이라 `sed`·`cat`·편집은 아무도 답하지 않는 권한 프롬프트에서 멈춘다.
- 보고에서 비밀처럼 생긴 값은 파일 경로나 변수 이름으로만 가리키고, `KEY=value`·`key: value` 꼴의 줄로 쓰지 않는다. 비밀 검사 hook 이 보고 전체를 막는다.

아래 거부 문단도 통째로 붙인다. 서브에이전트의 거부는 그 결과로 시작한 세션에 온다.

## 거부 문단

브리프와 서브에이전트 지시문에 요약하지 않고 통째로 붙인다(결정 255):

> 권한 규칙·권한 프롬프트, Claude Code 의 안전 검사(auto mode 분류기, 판정 없이 끝난 오류 포함), hook(비밀 검사 같은 가드 hook 포함), 사람이 거부한 행위는 거기서 멈춘다. 같은 행위를 다른 꼴로 다시 하지 않는다: 다른 세션·스크립트·도구·래퍼·대상으로, 명령을 쪼개서, 같은 결과를 내는 다른 확인으로 하는 것 모두 금지다. 여러 행위를 한 Bash 호출에 묶었다가 거부되면 그 안의 행위가 모두 거부된 것이다. 예외는 넷뿐이다. (1) hook 이 명령의 글만 맞춰 막았고 그 글이 명령이 여는 파일을 가리키지 않으면, 같은 명령 안에서 그 글만 한 번 고쳐 쓰고 보고에 그렇게 했다고 적는다. 스크립트나 다른 경로는 고쳐 쓰기가 아니다. (2) 같은 꼴로 한 번 더: 사람이 그 세션의 대화에서 허용했거나 규칙을 더했을 때, 또는 이유를 밝힌 분류기·hook 거부에 그 이유가 요구한 증거를 더했을 때만(사람의 거부에는 증거로 다시 하지 않는다). 보고에 "재시도 1회: <더한 증거>" 를 적는다. 두 번째 거부는 멈추고 보고한다. (3) sangsoe 의 `[gate:pressure]`·`[gate:sleep-loop]` 는 행위가 아니라 언제·어떻게 도는지만 막는다: 부하가 내려간 뒤 같은 호출, 같은 명령을 `run_in_background: true` 로. `[gate:self-land]` 는 빠진 걸음(`land`, `READY-WAIT` 줄, `merge_ready` 대신 worker_done)을 말하고, 그 걸음을 하고 다시 보내는 것은 재시도를 쓰지 않는다. (4) 브리프나 skill 이 그 일에 이미 정한 길(세션 시작은 `start_unit`, 머지는 `land`)로 가는 것, 그리고 `[gate:delegate]` 에 막힌 오케스트레이터가 그 일을 워커나 서브에이전트에게 넘기는 것은 다른 길이 아니다: 그 게이트는 오케스트레이터가 직접 하는 것만 막는다. 그 밖의 hook 거부는 다른 길을 일러 줘도 거부다. 거부된 명령 전문은 Write tool 로 `<TMPDIR 의 절대 경로, 없으면 /tmp>/orch-refusal/<worktree 폴더 이름>/<시각>.md` 에 쓴다. 브리프나 지시문이 작업 폴더 밖 쓰기를 막아도 이 파일은 쓴다. 처음 20줄 안에 `Act:` 로 시작하는 줄(하려던 행위)과 `Category:` 로 시작하는 줄(범주: 권한·분류기·no verdict·hook 이름·사람)을 둔다. 코어가 이 두 줄로 `refusal_report` 를 남기고, 없으면 그 거부는 보이지 않는다(결정 196). 그 Write 마저 거부되면 거부된 행위의 도구와 대상만 적는다. 보고는 같은 턴에 한 번, 일을 준 쪽 하나에 한다. 본문에 행위의 목적·범주·그 파일의 펼친 절대 경로(`$TMPDIR` 그대로가 아니라)를 쓰고 명령은 인용하지 않는다(그 글에 걸린 hook 이 보고까지 막는다). Dispatch 를 쥔 워커와 리드는 Orca escalation 으로 보낸다. Dispatch 가 없는 세션은 escalation 을 보내지 못한다(Orca 가 거부한다): Task 없는 리드는 오케스트레이터의 Run 에 `send --type question` 으로, 오케스트레이터는 `decision_open` 으로 오너에게 올린다. 이 길에는 `refusal_report` 행이 생기지 않는다. 서브에이전트는 Orca 메일을 보내지 못하므로 같은 것을 자기 결과에 쓴다: 파일 경로와 산문 설명만, `Act:`·`Category:` 줄은 결과에 옮겨 적지 않는다. 결과를 받은 세션이 그 거부를 자기 길로 올리고, 그 행위를 대신하지 않는다. 하나 다른 것: 서브에이전트의 Edit·Write 가 판정 없이(no verdict) 거부되었으면 그 서브에이전트를 멈추고, 시작한 세션이 그 단위를 처음부터 한 번 다시 한다. 다음 걸음은 리드나 오케스트레이터가 정한다. 실패한 검사(git hook·lint·시험·CI)는 거부가 아니다: 원인을 고치고 다시 돌린다.

## 쓰고 나서

받는 쪽이 이 브리프만 들고 완료 조건을 판정할 수 있는지 한 번 읽는다. "앞에서 말한", "아까 그" 같은 말이 남아 있으면 그 내용을 적는다.
