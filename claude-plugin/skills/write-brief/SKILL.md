# 브리프 쓰기

브리프는 새 세션이 가진 유일한 맥락이다. 받는 쪽은 너의 대화를 보지 못한다. 그래서 브리프는 "무엇이 끝인가"를 받는 쪽이 혼자 판정할 수 있게 쓴다. 모양(필수 칸, 형식)은 tool 이 검사한다. 여기서는 무엇을 쓰는지만 정한다.

## 칸

코어가 첫 줄에 역할 줄(`sangsoe-role: …`)을 붙인다. 브리프는 그다음 줄부터다. 역할 줄을 직접 쓰지 않는다.

| 칸 | 쓰는 것 |
|---|---|
| 목표 | 한 문장. 무엇을 바꾸거나 알아내는가 |
| 완료 조건 | 받는 쪽이 실행해서 확인할 수 있는 조건 목록. 조건마다 확인하는 명령이나 관찰을 붙인다. "잘 동작한다"는 조건이 아니다 |
| 범위 | 고쳐도 되는 경로와 고치면 안 되는 것. 임시 파일을 둘 곳. 남기는 checkout·등록·브랜치·파일·프로세스는 `resource_record` 로 기록하라는 줄(smoke·릴리스 단위에서 특히, 결정 240) |
| 맥락 | 읽어야 할 문서·결정 번호·관련 PR. 결론이 아니라 근거를 가리킨다 |
| 검증 | 어떤 증거가 필요한가. 머지가 걸린 일이면 검증 등급(V0–V3)이 정하는 증거. 확인 명령은 그대로 적는다. 증거는 리드가 `evidence_record` 로 기록하고, 워커는 실행 출력과 확인 못 한 것을 리드에게 보낸다(결정 171) |
| 계보 | 받는 쪽이 리드면, 단위의 세션은 MCP tool `start_unit` 으로만 연다(Task 없는 리드도, 결정 243). 받는 쪽이 워커면 이 칸 대신 아래의 "워커는 세션을 시작하지 않는다" 줄을 둔다 |
| 머지 | 리뷰 판정은 작성자가 아니라 리드가 `review_record` 로 기록한다(결정 111). 워커는 리뷰한 head·리뷰어·리뷰 원문의 위치를 리드에게 보낸다. 머지는 `land` tool 하나이고, 끝은 `merge_ready` 를 담은 worker_done 이다. 리드의 go 뒤에 머지하는 단위면 그 조건과, go 전에 보내는 worker_done 본문에 `READY-WAIT: <kind>` 줄을 둔다는 것을 여기 적는다. 그 줄이 없으면 `[gate:self-land]` 가 열린 PR 위의 worker_done 을 막는다(결정 201) |
| 승인 줄 | 오너의 말을 그대로 인용한 줄: `오너(dNNN, 날짜): "원문"`. 이 줄 밖의 일은 escalation 이다 |
| 보고 | 끝은 worker_done 한 번. 본문에 담을 것(바꾼 것, 증거, 확인 못 한 것, NOW·LATER·DROP 제안). 도중의 메시지는 다음 걸음으로 type 을 고른다: 답을 기다릴 메시지는 question 이다(워커는 `ask`), 답을 기다리지 않는 보고만 status 다 |
| 거부 | 아래 거부 문단을 그대로 붙인다 |

## 첫 프롬프트에 대해 알아둘 것

- Orca 는 워커의 첫 프롬프트를 자기 문구로 감싸 붙인다. 그래서 브리프 안의 `/goal` 줄은 워커·리드에게 걸리지 않는다. 끝나는 조건은 Dispatch 와 worker_done 이다. 완료 조건을 `/goal` 에 기대지 말고 본문에 쓴다.
- 워커는 세션을 시작하지 않는다. 브리프에 "도우미 워커를 띄워라"를 쓰지 않는다. 손이 더 필요하면 읽기 전용 서브에이전트나 리드에게 묻는 것이다.
- 보고 주소는 Run·Dispatch 다. 터미널 핸들(`term_…`)을 주소로 쓰지 않는다. 핸들은 재시작마다 바뀐다.
- 앞 워커가 끝난 뒤 도착한 답은 브리프에 섞지 않고 `start_unit` 의 `lateAnswers` 로 넘긴다.
- 모델 이름·effort 를 브리프에 적지 않는다. 단위의 종류는 `item_create`·`start_unit` 의 `class`(`default`·`hard`·`design`·`mechanical`·`docs`)로 표시한다(결정 187, 200). 브리프 본문에는 왜 그 class 인지 한 줄만 적는다. 문서만 바꾸는 단위는 `docs` 다.
- 워커가 advisor 를 언제 부르는지와 몇 번인지 한 줄 적는다: 접근을 정하기 전, 막혔을 때, 끝났다고 말하기 전, 행의 예산(resource `models` 의 `budget`) 안에서. 매 턴이 아니다. 예산 0 인 행과 예산을 다 쓴 단위는 advisor 가 꺼진 채 시작한다(결정 202).
- 행의 effort 가 high 아래면(resource `models` 로 본다) 완료 조건 앞에 한 줄을 넣는다: "일 전체를 끝까지 한다. 남은 일 목록이나 계속할지 묻는 말로 턴을 닫지 않고, 평범한 장애는 진단해 넘어간다." SessionStart 도 같은 줄을 주지만, 브리프가 받는 쪽의 유일한 맥락이므로 본문에도 둔다.
- 서브에이전트를 쓰라고 할 때는 그 `model` 을 resource `models` 의 `subagents` 로 정하라고 적는다(결정 188).

## 서브에이전트 지시문

브리프가 서브에이전트를 쓰게 하면, 그 지시문에 아래 두 줄을 넣으라고 적는다. 리드·오케스트레이터가 직접 쓰는 서브에이전트 지시문에도 넣는다.

- 하네스가 저장한 파일(tool-results, 백그라운드 task 출력)은 Read tool 로만 읽는다. 작업 폴더 밖이라 `sed`·`cat`·편집은 아무도 답하지 않는 권한 프롬프트에서 멈춘다.
- 보고에서 비밀처럼 생긴 값은 파일 경로나 변수 이름으로만 가리키고, `KEY=value`·`key: value` 꼴의 줄로 쓰지 않는다. 비밀 검사 hook 이 보고 전체를 막는다.

## 거부 문단

브리프와 서브에이전트 지시문에 요약하지 않고 통째로 붙인다:

> 권한 프롬프트·분류기·hook·사람이 거부한 행위는 다시 시도하지 않는다. 같은 형태로 한 번만 다시 시도할 수 있다 — 사람이 그 세션에서 허용했거나, 이유를 밝힌 분류기·hook 거부에 그 이유가 요구한 증거를 더했을 때만. 다른 세션·스크립트·도구로 같은 결과를 내는 것은 재시도가 아니라 금지다. 실행 방식만 막는 압박·sleep-loop 게이트는 행위의 거부가 아니라 안내를 따르는 것이다. 거부는 일을 준 쪽 하나에 바로 알린다: 행위의 목적, 거부의 범주(판정이 없었으면 "no verdict"), 명령 전문을 담은 파일의 경로(명령을 본문에 인용하지 않는다). 재시도했으면 "재시도 1회: <더한 증거>"를 적는다. 두 번째 거부는 멈추고 보고한다. 그 파일의 처음 20줄 안에 `Act:` 로 시작하는 줄(무엇을 하려던 행위인가)과 `Category:` 로 시작하는 줄(거부의 범주)을 둔다. 코어가 이 두 줄을 읽어 `refusal_report` 로 남기고, 두 줄이 없는 파일은 보이지 않는다(결정 196).

## 쓰고 나서

받는 쪽이 이 브리프만 들고 완료 조건을 판정할 수 있는지 한 번 읽는다. "앞에서 말한", "아까 그" 같은 말이 남아 있으면 그 내용을 적는다.
